Threat case study · DNS infrastructure

Poisoning the Cache:
radblok.co.za

A step-by-step walkthrough of how an attacker hijacks a domain by feeding a lie to the world's most trusted resolver — and why a missing cryptographic signature is all it takes.

Target: radblok.co.za Vulnerability: DNSSEC unsigned Resolver: 8.8.8.8 (Google) Status: unfixed
↗ radlee Lab Notes — Entry 007
01 — Background

How DNS caching creates the attack surface

When anyone types radblok.co.za into a browser, their device asks a recursive resolver — usually their ISP's, or Google's 8.8.8.8, or Cloudflare's 1.1.1.1 — to find the IP address. The resolver walks a chain: root nameservers, then ZARC for .co.za, then xneelo's nameservers, which give the real answer.

The resolver then caches that answer — saves it — and reuses it for every client who asks the same question, until a timer (the TTL) expires. It does not go back to xneelo each time. That cache is the attack surface.

There is no authentication in this chain. DNS runs over UDP — a fire-and-forget protocol with no handshake. The resolver cannot verify that a response is genuine. It trusts whoever answered first.

The caching problem Once a fake answer is in the cache, every person using that resolver gets the wrong IP — not just the person the attacker targeted. The cache is shared by millions of users.
02 — The attack

How an attacker plants a fake answer

This is the Kaminsky attack, published 2008. The core insight: if you can get a fake DNS response to the resolver before the real one arrives, the resolver accepts it as truth.

01
Attacker triggers a lookup
The attacker asks 8.8.8.8 to resolve radblok.co.za. If the answer isn't already cached, the resolver sends a query to xneelo's nameserver with a random transaction ID — say #4821 — to match the response to the question.
02
Attacker floods the resolver with fake replies
While 8.8.8.8 is waiting for xneelo to respond, the attacker sends thousands of forged UDP packets — each claiming to be from ns1.host-h.net, each with a different guessed transaction ID, all saying radblok.co.za = 45.33.100.1 (the attacker's server).
03
One fake reply wins the race
One of those thousands of fakes happens to carry #4821 — the same transaction ID the resolver is waiting for. It arrives a few milliseconds before xneelo's real reply. The resolver accepts it. The real reply arrives and is discarded — the cache already has an answer.
04
The lie is now cached
The resolver's cache now reads: radblok.co.za → 45.33.100.1. No error. No warning. From the resolver's perspective, it got a valid-looking response. Without DNSSEC, there are no signatures to check.
05
Every user is now redirected
Anyone whose device uses 8.8.8.8 and requests radblok.co.za now gets 45.33.100.1 — the attacker's server — for as long as the TTL holds. Could be an hour. Could be 24 hours. Millions of users share this cache.

03 — Victim impact

What the attacker does with a poisoned cache

Anyone hitting the poisoned resolver lands on the attacker's server. Their browser shows radblok.co.za in the address bar. The attacker has a clone of the site running at that IP.

Login forms
Fake login page harvests usernames and passwords. User never knows — the page looks identical.
not blocked
First HTTP visit
If the site redirects HTTP → HTTPS, the redirect itself hits the attacker's server first. That request is exposed before HTTPS ever fires.
not blocked
Inbound email (MX)
Attacker also poisons the MX record. All email to @radblok.co.za — password resets, business mail — routes to the attacker's mail server. Completely silent.
not blocked
New visitors
HSTS (the header that forces HTTPS on future visits) only applies after a first successful visit. A first-time visitor has no HSTS cache for this domain.
not blocked
HTTPS with cert
If the attacker obtains a fraudulent TLS cert for the domain — possible via a poisoned CA validation — the browser shows the padlock. Users see no warning at all.
partially blocked
The email angle is the most dangerous HTTPS protects web traffic. It does nothing for SMTP routing. A poisoned MX record redirects all inbound email to the attacker — password resets, business conversations, two-factor codes — with no warning anywhere in the chain.
04 — Defense

What DNSSEC does to stop this

DNSSEC adds cryptographic signatures to every DNS record. xneelo signs each record with a private key held in the zone. ZARC signs a DS record (a fingerprint of xneelo's key). The root signs ZARC's key. This creates an unbroken chain of trust from the root down to every individual record in the zone.

Root signs ZARC's key
ZARC (.co.za) signs zone key for radblok.co.za
radblok.co.za zone signs every record (A, MX, TXT…)

When the resolver receives any response about radblok.co.za, it checks the signature against this chain. A poisoned fake reply — even if it carries the right transaction ID — carries no valid signature. The resolver throws it away and returns SERVFAIL. The attack fails at the resolver, before the client ever sees a result.

kali — verify DNSSEC after enabling
# Should see RRSIG records and the 'ad' flag (authenticated data)
$ dig radblok.co.za A +dnssec

;; flags: qr rd ra ad; QUERY: 1, ANSWER: 2
radblok.co.za.  300  IN  A      X.X.X.X
radblok.co.za.  300  IN  RRSIG  A 13 3 300 ... (signature)

# Check DS record exists at ZARC level
$ dig radblok.co.za DS +trace
What changes for the attacker With DNSSEC enabled, the fake reply fails the signature check at 8.8.8.8. The resolver returns SERVFAIL instead of the poisoned answer. The attacker would need to compromise the zone signing key itself — a fundamentally different and much harder attack.
05 — Action items

Closing the gap on radblok.co.za

fix 1
Enable DNSSEC via xneelo. Log in to the xneelo control panel → DNS settings for radblok.co.za → enable DNSSEC. xneelo generates the zone keys, signs all records, and submits the DS record to ZARC automatically. Propagates in up to 48 hours.
fix 2
Add a CAA record. A CAA (Certification Authority Authorization) record tells every certificate authority which ones are allowed to issue TLS certs for your domain. Prevents fraudulent cert issuance even if a CA's validation is bypassed. Example: radblok.co.za CAA 0 issue "letsencrypt.org"
fix 3
Set an HSTS header with a long max-age. Once a visitor has seen the HSTS header, their browser enforces HTTPS for future visits without a round-trip to the server. Eliminates the HTTP-first window for returning users.
verify
Check with dig radblok.co.za A +dnssec after enabling. Look for RRSIG records in the answer section and the ad flag in the response header. Both present = chain of trust is working end to end.
